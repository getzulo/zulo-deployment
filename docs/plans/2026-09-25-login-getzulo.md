# login.getzulo.com — каталог аккаунтов и OAuth

**Решение, 2026-09-25: вариант B.** Каталог — свой сервис и своя база.
Control plane хранит стенды и `sub`, паролей клиентов у него нет.

Репозиторий: `getzulo/zulo-login`. Локально: `d:\Sources\zulo-login`, рядом с
`zulo-control-plane`. Обучение: `getzulo/zulo-learn`. Контейнеры `login` и
`learn` описаны в `prod/docker-compose.accounts.yml` и работают на `zo-app-1`.

**Код.** Страница пароля, регистрация, подтверждение, сброс, сессия каталога
и OAuth 2.0 / OIDC: `/authorize`, `/token`, JWKS, userinfo, refresh с
ротацией. SMTP ещё нет. Проверка: `dotnet test` в `zulo-login`.

Этот файл пересматривает строку «аккаунты остаются в control plane» из
[`2026-09-23-cabinet-and-learning.md`](2026-09-23-cabinet-and-learning.md) и из
спеки `zulo.one/docs/superpowers/specs/2026-09-23-cabinet-and-learning-portal.md`.

## Что этот хост должен уметь

`login.getzulo.com` — точка входа в том же смысле, в каком
`login.microsoftonline.com` является точкой входа Microsoft. Кабинет на
`getzulo.com` и портал `learn.getzulo.com` пароль не спрашивают. Оба, и любое
следующее приложение, приходят сюда за сессией.

Образец у Microsoft устроен так:

| У Microsoft | Что это на самом деле | У нас |
|---|---|---|
| `login.microsoftonline.com` | протокол каталога Entra ID, не страница портала Azure | `login.getzulo.com` |
| каталог пользователей, приложения, согласия, ключи подписи | данные Entra, своя база | каталог Zulo |
| Azure Resource Manager | подписки и ресурсы, хранит object id из каталога, не пароль | control plane: стенды, провижининг, биллинг |
| портал Azure, Office, Graph | клиенты OAuth | кабинет, learn, позже сам ERP |

Протокол, без которого это не «как Microsoft», а самодельная пересылка кода
между двумя нашими сайтами:

- OAuth 2.0: `authorization_code` + PKCE, `refresh_token` с ротацией;
- OpenID Connect: discovery, JWKS, `id_token`, userinfo, end session;
- несколько способов доказать личность у одного человека: пароль, TOTP,
  Google, Apple;
- тихий вход: сессия есть на хосте login — приложение получает код без формы;
- отдельный выход из одного приложения и выход из каталога целиком.

SAML, гостевой B2B и каталог организации в первую очередь не входят. Схема
каталога не должна делать их невозможными.

Профиль — тоже только здесь, как `myaccount.microsoft.com` / аккаунт Google.
Страница `/account`: имя, телефон, язык, фото (JPEG/PNG/WebP, до 256 КБ).
Иконка отдаётся с `/a/{ключ}`, ключ не равен Guid аккаунта. Клиенты
(getzulo.com, кабинет, learn, cp.zulo.one) не правят профиль сами: рисуют
чип `zulo-person` / `zulo-person-mark` / `zulo-person-text` и ведут сюда.
Канон CSS — `/person.css`. `/userinfo` и `/session` читают карточку из базы,
не из JWT, иначе смена фото видна только после refresh.

## Что есть сегодня

Личность клиента уже отделена от оператора. `CustomerAccount` и
`OperatorAccount` — разные таблицы, разные сессии, разные схемы. Это
правильная граница, и её трогать не надо: операторский break-glass на
`login.getzulo.com` не переезжает.

Личность клиента при этом лежит в той же базе, что и флот:

| Таблица | Зачем |
|---|---|
| `CustomerAccounts` | почта, bcrypt, TOTP, блокировка, `EmailVerifiedAt` |
| `CustomerSessions` | opaque bearer, в базе только SHA-256 |
| `CustomerTokens` | одноразовые ссылки verify / reset |
| `TenantMemberships` | аккаунт × стенд × `Owner`/`Member`, FK на обе стороны |

`TenantClaimService` при верификации и при каждом входе выдаёт стенды, у
которых `Tenant.AdminEmail` совпал с подтверждённой почтой. Без
подтверждения захват стенда по набранному адресу был бы тривиален.

`PasswordHash` сейчас обязателен. Второй способ входа (Google, Apple) в эту
форму не ложится: у человека должен быть набор удостоверений, а не одна
колонка пароля.

Портал в проде не включён (`Portal:Enabled = false`, писем клиентам не
уходило). Перенос каталога сегодня не двигает живых людей. Локальные
dev-аккаунты можно выбросить.

## Три места, где может жить каталог

### A. Каталог остаётся в control plane, login — сайт-фасад

`login.getzulo.com` рисует форму и по внутренней сети зовёт уже написанные
`/api/portal/auth/*`. Пароль, TOTP и сессия по-прежнему строки control plane.
Приложения получают тот же opaque bearer, что кабинет получает сегодня.

Так дешевле начать: регистрация, письма, блокировка и самозахват стенда уже
покрыты тестами.

Граница от этого не появляется. Хост, который умеет удалить базу клиента,
продолжает хранить его пароль. OAuth оказывается надстройкой над ручками
кабинета, а не протоколом каталога. Стороннее приложение и learn ходят в ту
же базу, что операторская панель. Именно это и не нравится в исходном
решении.

### B. Каталог — свой сервис за `login.getzulo.com`, у control plane только subject

Отдельный процесс и отдельная база. Сайт `login.getzulo.com` — его
публичная поверхность: формы и OAuth/OIDC. Control plane перестаёт знать,
как человек вошёл. Он хранит стабильный `sub` и решает, какие стенды этому
`sub` доступны.

Это то же разделение, что у Entra и Azure Resource Manager.

Переносится написанное: хеш пароля, TOTP, письма, рейт-лимит, одноразовые
токены. Связь «человек ↔ стенд» теряет FK и становится контрактом: каталог
утверждает `sub` и подтверждённую почту, control plane по ним ведёт
membership. Две базы, два бэкапа, нет каскада «удалили тенант — удалили
человека».

### C. Отдельный процесс, та же база control plane

Сайт отдельный, таблицы каталога остаются в Postgres флота, только в другой
схеме. Деплой выглядит независимым, компромисс базы — общий. FK между
membership и аккаунтом снова оказывается под рукой, и через полгода каталог
опять «просто часть панели».

Отдельность хоста без отдельности данных задачу не закрывает.

**Дальше в этом файле расписан вариант B.** A оставлен как более дешёвый
путь, если решим, что вторая база сейчас дороже границы.

## Вариант B: кто что хранит

### Каталог (база login)

Личность и способы входа. Один человек — много удостоверений.

```
Account
  Id              sub, стабильный, не почта
  Email           lower-case, уникален
  EmailVerifiedAt
  DisplayName
  Locale
  Kind            personal          — организация позже, колонка есть сразу
  FailedAttempts
  LockedUntil
  CreatedAt

Credential
  AccountId
  Type            password | totp | google | apple
  Subject         sub провайдера; у пароля пусто
  Secret          bcrypt | секрет TOTP | ничего у федерации
  LastTotpStep    защита от повторного кода
  UNIQUE (Type, Subject) где Subject задан

DirectorySession
  сессия самого login.getzulo.com
  хеш opaque-куки, срок, отзыв
  это то, что даёт тихий SSO между приложениями

Client
  ClientId        cabinet | learn | …
  RedirectUris    белый список, без чужого origin
  Kind            confidential (наш BFF) 

AuthorizationCode
  хеш, client_id, redirect_uri, code_challenge, nonce, sub, срок, ConsumedAt

RefreshToken
  хеш, client_id, sub, ротация, семья токенов (повтор старого гасит семью)

OneTimeToken
  verify | reset, хеш, ConsumedAt
  те же правила, что у сегодняшнего CustomerToken
```

Пароль больше не колонка аккаунта. Аккаунт без пароля законен: человек вошёл
через Apple и пароля у него нет. Отвязать последнее удостоверение нельзя —
сегодня это планировалось проверкой в кабинете, здесь это правило каталога.

Связывание Google/Apple с уже существующей почтой — то же правило, что в
спеке кабинета: автоматически только когда провайдер прислал
`email_verified` и у аккаунта почта уже подтверждена. Иначе это захват
ящика.

### Control plane

Флот. Про человека он знает `sub` и подтверждённую почту, которые пришли в
токене.

```
TenantMembership
  Subject         sub из каталога, не FK
  EmailAtGrant    какая почта была подтверждена в момент выдачи
  TenantId
  Role            Owner | Member
  GrantedBy
  UNIQUE (Subject, TenantId)
```

`Tenant.AdminEmail` остаётся фактом провижининга: для кого собрали стенд.
Самозахват переезжает сюда в урезанном виде. Каталог его не выполняет —
каталог не знает, что такое стенд. При входе в кабинет control plane видит
токен с `email_verified` и делает то, что сегодня делает
`TenantClaimService`: нет владельца и почта совпала — этот `sub` становится
`Owner`. Неподтверждённая почта по-прежнему не захватывает ничего.

Приглашение участника: строка control plane (почта, стенд, роль). Человек
входит через login, подтверждённая почта совпала — в membership пишется его
`sub`.

`OperatorAccount` остаётся в control plane, со своей схемой входа, за
Cloudflare Access. Путать его с каталогом клиентов — смешать break-glass с
публичной регистрацией.

### Приложения

Кабинет и learn аккаунтов не хранят. У каждого своя запечатанная кука на
своём хосте. Внутри — access token каталога, не bearer control plane.

Кука login не уходит на `getzulo.com` и не уходит на `learn.getzulo.com`.
Общей куки на `.getzulo.com` нет: иначе сессия каталога уедет на витрину и
на любой будущий поддомен.

## Протокол

Публично на `login.getzulo.com`:

| Путь | Кто зовёт |
|---|---|
| `/.well-known/openid-configuration` | приложения, при старте |
| `/authorize` | браузер |
| `/token` | сервер приложения (BFF), не браузер |
| `/jwks` | кто проверяет подпись |
| `/userinfo` | BFF |
| `/logout` | браузер, end session |
| формы login, register, verify, reset, выбор способа входа | браузер |

Поток кабинета и learn один:

```
браузер → приложение → 302 login/authorize
          state, nonce, code_challenge S256, client_id, redirect_uri
login    сессии каталога нет → форма на этом хосте
         сессия есть → пароль не спрашивается
         → 302 обратно ?code&state
BFF      POST /token  code + code_verifier + client secret
         ← access JWT (минуты) + id_token + refresh (только BFF)
BFF      кладёт access в свою запечатанную куку
```

Access — JWT, подпись ключом каталога, `iss=https://login.getzulo.com`,
`aud` равен клиенту, `sub` — id аккаунта. Control plane проверяет подпись по
JWKS и по `sub` читает membership. Opaque bearer кабинета для этого больше
не нужен: его нельзя проверить, не спросив базу control plane, а у Microsoft
ресурс как раз проверяет токен каталога сам.

Отзыв живёт на refresh и на сессии каталога. Короткий access доживает свои
минуты — это обычная цена JWT. Выход из learn удаляет refresh этого
клиента. «Выйти везде» удаляет `DirectorySession` и все refresh этого
`sub`: тихий `/authorize` снова показывает форму, остальные приложения при
следующем refresh получают отказ.

Код авторизации — одноразовый, на минуту, привязан к `client_id`,
`redirect_uri` и `code_challenge`. Хранится хеш, как у сегодняшнего
`CustomerToken`. Повтор использованного кода — отказ, не второй вход.

Google и Apple завершаются на `login.getzulo.com`. Один redirect у
провайдера на всех наших приложений. Apple по-прежнему отдаёт имя и почту
только в первый раз, client secret живёт не дольше полугода, Private Relay
требует зарегистрированного домена. Это свойство Apple, хост его не отменяет.

Письма verify и reset шлёт каталог. Ссылка ведёт на `login.getzulo.com`, не
на `/cabinet/verify`. То, что в треке D5 уже прописано на кабинет, при
выборе B переносится.

## Страница входа

У `login.getzulo.com` своя страница, в том же смысле, что у
`login.microsoftonline.com`. Пароль вводится только здесь. Кабинет и learn
поле пароля не рисуют.

Страница открывается из `/authorize`, когда сессии каталога нет. На ней
написано, какое приложение просит вход. Если сессия уже есть, это кнопка
«продолжить» под текущим адресом. Прямой заход на хост ведёт в управление
своим входом: пароль, TOTP, Google, Apple.

Форма рисуется только после проверки `client_id` и точного `redirect_uri`.
Незарегистрированный клиент получает отказ. Страница с логотипом и полем
пароля для чужого адреса возврата превращает наш хост в фишинг.

Сама страница:

- не вкладывается во фрейм (`frame-ancestors 'none'`);
- грузит скрипты только со своего хоста, без аналитики и чужих шрифтов;
- принимает пароль только в теле POST, с антифоргери;
- не отдаёт referrer наружу;
- держит стабильный URL и обычный `autocomplete`, чтобы менеджер паролей
  заполнял только этот хост.

Кука сессии каталога — `__Host-`: `Secure`, `HttpOnly`, `Path=/`, без
родительского домена, `SameSite=Lax`. `Strict` не пришлёт куку при возврате
с Google и Apple.

Ответы формы переносятся из кабинета и при переезде не ослабляются.
Неизвестный адрес, неверный пароль и блокировка звучат одинаково, блокировка
проверяется до bcrypt. «Почта не подтверждена» говорится только после верного
пароля. Письмо подтверждения не уходит с неудачного входа и не уходит на уже
подтверждённый адрес. Код TOTP одноразовый. Рейт-лимит бережёт процессор,
граница — блокировка аккаунта. Ссылка из письма хранится хешем. `redirect_uri`
сверяется побайтово.

### Cloudflare перед хостом

Хост стоит за прокси Cloudflare, как публичный сайт: оранжевое облако, WAF,
origin снаружи не открыт. Файрвол уже пускает на такие адреса только префиксы
Cloudflare.

Это не Cloudflare Access. Access — стена панели оператора: чужой браузер до
приложения не доходит, внутри ещё allowlist почты. Поставить ту же стену
перед `login.getzulo.com` значит пустить на страницу входа только сотрудников.
Клиент до формы не доберётся.

Прокси закрывает объём: сеть, подбор с тысяч адресов, прямой заход на IP
машины. Он не проверяет `redirect_uri`, не отличает «ящика нет» от «пароль
неверный» и не подписывает токен. Эти проверки остаются в приложении. Access
на панели устроен так же: облако впереди, решение о допуске всё равно в коде.

Практические правила именно для страницы входа за прокси:

- HTML страницы, `POST` формы, `/authorize` и `/token` не кешируются. В кеш
  можно отдать discovery и JWKS, коротким сроком. Закешированная форма несёт
  протухший антифоргери-токен, закешированный `/authorize` — чужой вход.
- Приложение верит `CF-Connecting-IP` только если соединение пришло с
  префикса Cloudflare. Иначе заголовок подделывается и рейт-лимит смотрит не
  на того.
- JS-челлендж и режим «я под атакой» не включаются на колбэках Google и
  Apple. Apple шлёт `form_post` без браузерного скрипта; челлендж съедает
  тело, и это выглядит как сломанный Apple.
- Капча на каждый вход не ставится отдельным экраном. На шаге пароля и на
  сбросе стоит Cloudflare Turnstile (`appearance: interaction-only`): человек
  почти не видит её, бот — видит. Сервер проверяет токен через Siteverify.
  Production без ключей отказывает в посте пароля.

## Панель оператора

Cloudflare Access Application перед `cp.zulo.one` не используется. Панель —
OAuth-клиент `controlplane` с `redirect_uri=https://cp.zulo.one/signin-oidc`.
Пароль вводится на `login.getzulo.com`, затем Telegram. Кука панели
`__Host-zulo_cp`. Break-glass на порту 5099 без изменений.

В Cloudflare Zero Trust удалить Access Application, который закрывал
`cp.zulo.one`. Оранжевое облако, WAF и ограничение origin префиксами Cloudflare
остаются. Создать виджет Turnstile на `login.getzulo.com` (Managed), ключи — в
`login.env` (`Turnstile__SiteKey`, `Turnstile__Secret`). Секрет клиента панели
один и тот же в `login.env` (`Oauth__Clients__2__ClientSecret`) и в `cp.env`
(`Directory__ClientSecret`). Контейнер логина на `zo-edge0` по умолчанию не
ходит в интернет: без `LOGIN_HTTPS_HOSTS` в `container-egress.sh` Siteverify и
Telegram 2FA таймаутятся, хотя виджет в браузере рисуется.

## Чего в первой очереди нет

- Каталог организации (`Kind=organization`) и вход «рабочим» аккаунтом.
  Колонка `Kind` есть, строки такой нет.
- Публичная регистрация чужих OAuth-клиентов. Таблица `Client` есть,
  строки заводим мы: `cabinet`, `learn` и `controlplane`.
- SAML, device code, client credentials.
- Общая кука на родительском домене.
- Cloudflare Access на `login.getzulo.com` и на `cp.zulo.one`. Перед хостами только прокси.

ERP-тенант клиента позже может стать третьим `Client` с тем же `sub`.
Отдельной учётной записи «пользователь стенда» этот каталог не заменяет:
люди внутри ERP остаются пользователями тенанта. Каталог — про человека,
который входит на наши сайты.

## Где лежит код

Отдельный репозиторий, не папка внутри control plane и не приложение внутри
`getzulo.com`. Иначе каталог снова оказывается модулем флота или модулем
витрины, и граница из варианта B существует только на слайде.

| | |
|---|---|
| GitHub | `getzulo/zulo-login` (remote создаётся вместе с первым коммитом) |
| Диск | `d:\Sources\zulo-login` |
| Процесс | один: формы входа и OAuth/OIDC |
| База | своя Postgres, не база control plane |
| Стек | ASP.NET, как control plane. Форма и `/authorize` живут в одном процессе: второй Next-фронт на этом хосте ничего не разделяет |
| Рядом в Cursor | папка добавляется в воркспейс вручную, сама она в текущие корни не входит |

`getzulo.com` остаётся витриной и клиентом `cabinet`.
`zulo-deployment` по-прежнему описывает, как оба процесса поднимаются на хосте.

Портал обучения — тоже свой репозиторий, не раздел кабинета и не зона
`getzulo.com`.

| | |
|---|---|
| Хост | `learn.getzulo.com` |
